Invoke the `customer-experience-excellence` skill, read `references/accessibility.md` in full, then run the **WCAG 2.2 Level AA release gate** against:

$ARGUMENTS

If no scope is given, audit the uncommitted changes in the working tree; if the tree is clean, audit the changes on the current branch against `main`.

Work through the reference's required verification in order:
1. Run the repository's own accessibility checks (axe-core, Playwright accessibility assertions, eslint-plugin-jsx-a11y or equivalent) if they exist. Report the exact commands and their real output.
2. Test keyboard-only completion of the task: tab order, visible focus, dialogs, dropdowns, form errors, focus restoration, keyboard traps.
3. Check screen-reader behavior if a screen reader is available; otherwise mark it **not verified** and request human QA. Do not infer it.
4. Check text and non-text contrast, 200% and 400% zoom/reflow, a small mobile viewport, and reduced-motion.
5. Map every observed violation to a specific WCAG 2.2 success criterion — verify the criterion ID before citing it, and do not invent one.

Report as a table of findings: criterion → severity → location (`file:line` or screen/state) → customer consequence → fix → retest outcome. Follow it with:
- **Blockers** — known applicable Level A/AA failures in changed scope.
- **Needs manual verification** — risks you could not confirm in this environment.
- **Outside our control** — third-party checkout or booking components, with the vendor boundary documented.

Never claim conformance on the strength of automated checks alone. Always close with the residual risks and the manual checks a human still has to do.
